# 单程目录结构

版本：V0.1

本文基于以下单程资料样例整理：

```text
/media/haiming/data2/2026_test/0521_ramp/7869148/pipeline/public/MX11-2S/HXMQBC7PZ4CT25SL1/2026-03-21/110247/110557/644470719
```

当前版本先按真实样例归纳目录结构，不把样例中没有验证到的内容写成强规范。标注为“待确认”的部分需要后续和数据生产方、算法链路或更多样例共同收敛。

## 1. 根目录命名

样例路径可拆成：

```text
<dataset_root>/<scene_or_batch>/<group_id>/pipeline/public/
└── <vehicle_model>/<vin>/<date>/<start_time>/<end_time>/<track_id>/
```

对应样例：

| 层级 | 样例值 | 说明 |
|---|---|---|
| `vehicle_model` | `MX11-2S` | 车型或平台名，待确认是否固定来自车端元信息 |
| `vin` | `HXMQBC7PZ4CT25SL1` | 车辆 VIN |
| `date` | `2026-03-21` | 采集日期 |
| `start_time` | `110247` | 起始时刻，格式疑似 `HHMMSS` |
| `end_time` | `110557` | 结束时刻，格式疑似 `HHMMSS` |
| `track_id` | `644470719` | 单程轨迹 ID 或资料 ID，命名来源待确认 |

待确认：`start_time/end_time` 是否一定是本地时间 `HHMMSS`，以及 `track_id` 是否全局唯一。

## 3. 根目录文件

根目录文件主要是传感器标定、定位、感知和局部地图帧数据。

| 文件 | 样例顶层结构 | 说明 |
|---|---|---|
| `calib.json` | object，含 `antenna/cameras/imu/lidars` | 传感器外参/内参标定 |
| `camera.json` | object，按相机名组织 | 相机相关配置或元信息 |
| `lidar.json` | object，按雷达名和版本组织 | 雷达相关配置或元信息 |
| `loc.json` | array | 定位摘要或轨迹数据，具体语义待确认 |
| `InfoLocalization.csv` | CSV | 定位信息表 |
| `localization_geodetic_localization.json` | array | 大地坐标定位数据 |
| `localization_kinetic_localization.json` | array | 车辆/惯导运动定位数据 |
| `optimized_keyframe_poses.json` | array，样例 191 条 | 根目录下的优化关键帧位姿 |
| `perception_frame_traffic_light.json` | array | 红绿灯感知帧 |
| `perception_frame_traffic_sign.json` | array | 交通标志感知帧 |
| `perception_fusion_obstacles.json` | array | 障碍物融合感知帧，样例文件较大 |
| `perception_surround_localization.json` | array | 环视/感知侧定位数据 |
| `road_model_surround_local_map.json` | array | 环视局部地图帧或矢量观测数据 |

注意：样例根目录也存在 `optimized_keyframe_poses.json`，同时算法结果目录下也存在 `results/optimized_keyframe_poses.json`。本样例二者长度均为 191；是否内容完全等价、以及下游应优先读取哪一份，需要进一步确认。

## 11. 和线上多程结构的区别

当前样例是单程资料目录，不是线上多程资料组目录。主要差异：

| 对比项 | 单程样例 | 线上多程资料组 |
|---|---|---|
| 根目录入口 | `<vehicle_model>/<vin>/<date>/<start>/<end>/<track_id>` | `thrd_multi_handle` 或资料组根目录 |
| 轨迹数量 | `slam_tracks.json` 样例 1 条 | `exp_tracks.json` 可包含多条 track |
| 根目录是否有 `vision_mapping/` | 样例没有 | 多程资料组一般有 `<base_dir>/vision_mapping/results/...` |
| 单程矢量结果 | `deep-learning/vision-map/<run_id>/results/vm_post_process/` | 每个 segment 下的 `vision_mapping/results/vm_post_process/` |
| 多程过程输出 | 样例没有 `cs_tracks/` | 多程 online pipeline 输出 `vision_mapping/results/cs_tracks/` |

因此，不建议把线上多程的 `vision_mapping/results/fusion_filter_result/exp_tracks.json`、`vector_pb_data/`、`cs_tracks/` 结构直接套用到这个单程样例上。

## 12. 待确认问题

1. 单程根目录命名中的 `track_id` 是否全局唯一，是否等价于业务资料 ID。
2. `start_time/end_time` 是否一定是本地时间 `HHMMSS`，是否可能跨天。
3. `deep-learning/vision-map/<run_id>` 是否会有多个 run；如果有多个，下游如何选择有效 run。
4. 根目录 `optimized_keyframe_poses.json` 与 `results/optimized_keyframe_poses.json` 的权威关系。
5. `road_model_surround_local_map.json` 是否等价于后续线上结构中的 `vector_data.json` 输入，还是只是一类原始局部地图帧。
6. `camera.json` 中存在但 `camera/` 目录未落盘的相机，是未采集、被裁剪，还是当前算法不使用。
7. `trajectory_length.txt` 的单位是否为米。
8. `track_secs.json` 的字段语义和下游用途。
9. `traffic_light.json` 是否应纳入单程 `vm_post_process` 标准输出清单。
10. `version_single.txt` 的值是算法版本时间、镜像构建时间，还是后处理脚本版本。

## 13. 推荐规范化口径 V1

在下一版规范中，可以先把单程目录拆成三类入口：

1. 资料根目录：相机、点云、定位、感知、标定、局部地图原始数据。
2. 算法 run 目录：`deep-learning/vision-map/<run_id>/`，记录一次视觉建图处理的日志、SFM、评估和可视化产物。
3. 标准矢量输出目录：`deep-learning/vision-map/<run_id>/results/vm_post_process/`，作为单程矢量消费方优先读取的结果目录。

其中 `vm_post_process/` 可以先作为最稳定的下游接口，根目录和 `results/` 中的大文件则按数据来源和算法阶段分别说明。
